# 驗證結果與限制

[← 回 README](../README.md)

## 驗證範圍

- 程式是在**沒有音效裝置**的雲端 Linux 環境開發的。
- 這一頁大部分的數字是在 **Python 版（v0.3.1）** 上量的。v0.4.0 起改用 Rust 重寫，DSP 照同樣的設計移植、測試照搬並用同樣的門檻；Rust 版自己的數字見 [Rust 版（v0.4.0）](#rust-版v040)。
- **Rust 版還沒在實機上長時間使用過**。下面「實機使用」的結果都是 Python 版的；Rust 版用的是同一套 WebRTC 回聲消除。

**實機使用（Python 版）**

- 桌上型喇叭 + 桌上型麥克風，Discord 通話：回聲消除有效，對方聽不到回音。
- Discord 的噪音抑制開 Krisp 時，回聲消除照常有效，還能去除機械鍵盤聲。
- Hey Siri 防誤觸：只削 3 kHz 以上的設定都擋不住（30 dB 的窄頻陷波；v0.4.5 的「一直處理 + 標準」2.8–6.5 kHz 70 dB 也被叫醒）。v0.4.6 的新強度（1–6.5 kHz）和 `heysiri` 模式用 `--siri-test` 的音檔實測過一次（見下方）；「降低其他聲音」還沒在實機上測過。
- 4K 螢幕：視窗大小、文字與圖示顯示正常（v0.2.0 起）。

**離線驗證（Python 版）**

- 所有聲音處理都用合成訊號和 TTS 語音做過離線測試。
- 跑過模擬多個裝置、各自時脈不同的多執行緒整合測試。
- Windows 版 exe 在 GitHub 的 Windows 機器上打包，並跑過自我檢測：
  - 引擎能載入、離線回聲消除量正常
  - Siri 陷波有作用
  - 圖示有包進 exe
- 完整測試也在 Windows 上跑過，全部通過。

## Rust 版（v0.4.0）

| 項目 | 結果 |
|---|---|
| webrtc ERLE | 41.2 dB |
| speex ERLE | 21.0 dB |
| nlms ERLE | 18.6 dB |
| Siri 陷波（4 kHz 頻帶） | −70 dB |

**移植過來的測試**（`cargo test`，合成訊號，遠端單講時的 ERLE、40 ms 延遲）

| 引擎 | 降噪關 | 降噪開 |
|---|---|---|
| webrtc | **43.2 dB** | **55.3 dB** |
| speex | 27.1 dB | 38.6 dB |
| nlms | 31.7 dB | — |

**資源用量**

- 整條處理流程每 10 ms 音框約 0.27–0.34 ms CPU（Linux，機器同時有其他負載）。
- 記憶體（RSS）約 24 MB；Python 版約 130 MB。
- 連續開始 / 停止 20 次，執行緒數和記憶體都沒有增加。

**還沒驗證的**

- Rust 版還沒在接真實麥克風 / 喇叭 / VB-Cable 的電腦上長時間使用過。遇到問題可以先改用 [v0.3.1](https://github.com/samfeng0517/desk-echo-guard/releases/tag/v0.3.1)（設定檔共用）並開 issue 回報。

## 回聲消除

以下是 Python 版（v0.3.1）的量測；Rust 版的數字見 [Rust 版（v0.4.0）](#rust-版v040)。

**測試方式**

- 麥克風訊號 = 近端語音 + 房間脈衝響應 × 延遲後的參考 + 雜訊。
- 房間脈衝響應包含直達聲和 200 ms RT60 的尾音。
- 依序跑三段：只有遠端講話 40%、只有近端講話 20%、雙方同時講話 40%。

**表格說明**

- ERLE：回聲衰減量，越大越好。
- STOI：清晰度，1 = 完全不變。

### TTS 語音（遠端女聲、近端男聲；Python 版的 `experiments/aec_tts_eval.py`）

| 引擎 | 降噪 | 延遲 | ERLE | 近端單講 STOI | 雙講 STOI：輸出（原始麥克風） |
|---|---|---|---|---|---|
| webrtc | 關 | 40 ms | **41.9 dB** | 1.00 | 0.59 (0.74) |
| webrtc | 開 | 40 ms | **53.9 dB** | 0.99 | 0.55 (0.74) |
| webrtc | 關 | 150 ms | 42.2 dB | 0.99 | 0.60 (0.74) |
| speex | 關 | 40 ms | 23.5 dB | 0.99 | **0.98** (0.74) |
| speex | 開 | 40 ms | 43.3 dB | 0.97 | **0.94** (0.74) |
| speex | 開 | 150 ms | 38.1 dB | 0.95 | 0.94 (0.74) |
| nlms | — | 40 ms | 18.0 dB | 1.00 | 0.92 (0.74) |

### 合成訊號（類語音的脈衝列 + 共振峰 + 摩擦音 + 停頓；Python 版的 `pytest`）

| 引擎 | 降噪 | 延遲 | ERLE | 近端單講：音量變化 / STOI | 雙講 STOI：輸出（原始麥克風） |
|---|---|---|---|---|---|
| webrtc | 關 | 40 ms | **42.0 dB** | −0.4 dB / 0.99 | 0.64 (0.70) |
| webrtc | 開 | 40 ms | **54.1 dB** | −0.4 dB / 0.99 | 0.62 (0.70) |
| webrtc | 關 | 150 ms | 42.2 dB | −0.4 dB / 0.99 | 0.61 (0.68) |
| speex | 關 | 40 ms | 25.9 dB | −2.1 dB / 0.99 | 0.92 (0.70) |
| speex | 開 | 40 ms | 39.1 dB | −2.2 dB / 0.93 | 0.90 (0.70) |
| speex | 關 | 150 ms | 22.4 dB | −2.1 dB / 0.99 | 0.92 (0.68) |
| nlms | — | 40 ms | 25.9 dB | −0.1 dB / 1.00 | 0.87 (0.70) |
| nlms | — | 150 ms | 14.7 dB | −0.1 dB / 1.00 | 0.89 (0.68) |

### 其他項目

- **時脈漂移**
  - 生產端 ±500 ppm 時，估計值為 499.5 / −499.8 ppm。
  - 水位維持在 10–20 ms，沒有欠載。
- **整合測試**
  - 完整多執行緒程式接上模擬裝置：loopback +100 ppm、CABLE −60 ppm。
  - ERLE 約 40–41.6 dB，沒有欠載。
- **延遲估計（GCC-PHAT）**
  - 誤差 < 1 ms。
  - 參考訊號晚到（負延遲）也能正確判讀。
- **延遲補償**
  - 延遲 600 ms 時，NLMS 的 ERLE 是 −2.8 dB。
  - 加上 `--delay-ms 590` 後變成 17.5 dB。
- **測試中發現的 AEC3 行為**
  - 輸入接近滿刻度，或出現極不自然的大聲嘶聲時，AEC3 會停止消除，很久不會恢復。
  - TTS 語音沒有遇到這個狀況。
  - 這是程式會提醒「麥克風太大聲」的原因（見[常見問題](faq.md#出現麥克風太大聲的警告)）。

## Hey Siri 實機測試（v0.4.6）

用 `--siri-test` 產生的 32 個音檔（4 個內建合成聲音 × 4 種設定 × 2 次，順序打亂），一位使用者測一輪的結果。

- 播放：平常通話用的那組桌上型喇叭。
- 裝置：同一個房間的 HomePod mini（第一代）為主；房間外的 HomePod（第二代）也有幾次被叫醒。只要有任何一台被叫醒就算「被叫醒」，沒有分開記是哪一台。


| 設定 | 被叫醒（全部） | 被叫醒（扣掉男聲 B） |
|---|---|---|
| 原音（對照組） | 6 / 8 | 6 / 6 |
| `always` + `deep-wide` | 1 / 8 | 1 / 6 |
| `heysiri` + `deep-wide` | 1 / 8 | 1 / 6 |
| `heysiri` + `early` | 1 / 8 | 1 / 6 |

- 「內建男聲 B」的原音兩次都沒叫醒 Siri，所以它的題目不能算（右欄）。
- 1–6.5 kHz 的陷波在實機上有效：6/6 降到 1/6（Fisher 精確檢定單尾 p ≈ 0.008）。
- 三種設定之間看不出差別；每種 6 次，分不出 1/6 和例如 0/6、2/6。
- 被叫醒的三題（21、24、30）各是不同的題目，同一聲音同一設定的另一題都沒叫醒。事後把這三題各重播一次，兩台 HomePod 都沒有再被叫醒，所以是在觸發邊緣的偶發結果，不是某個聲音或某種設定固定擋不住。
- 沒有涵蓋的：真人的聲音（偵測器只用合成語音訓練過，而且這 4 個聲音在訓練資料裡）、經過通話軟體壓縮的聲音。
- 沒有測 iPhone（它會比對主人的聲音，合成聲音多半叫不醒）。

## Hey Siri 陷波

以下是 Python 版（v0.3.1）的量測，強度是當時的定義（`deep-wide` = 2.8–6.5 kHz、`formant` = 1–3 kHz + 四個窄帶）；v0.4.6 的新定義見表格最後幾列（`formant` 已移除）。

| 項目 | 結果 |
|---|---|
| `deep-wide`（合成語音）：目標頻帶衰減 / 總能量 / 頻帶外 LSD / STOI | ≥ 45 dB / −0.23 dB / 0.00 dB / 0.97 |
| `apple-deep`（合成語音）：目標頻帶衰減 / 總能量 / 頻帶外 LSD / STOI | ≥ 32 dB / −0.13 dB / 0.01 dB / 0.99 |
| `formant`（合成語音）：目標頻帶衰減 / STOI | ≥ 32 dB / 0.89 |
| `sibilant` 模式（v0.4.1，合成「s」音；v0.4.6 已移除此模式） | 總延遲 72.5 ms；從「s」音開頭起的前 10 ms 目標頻帶就衰減約 59 dB（區塊大小 1–1000 樣本都一樣，偵測區段從不被截掉開頭） |
| `detect` 模式（Python 版，用已知位置的假偵測器測；v0.4.1 已移除此模式） | 只有那一句被改，其他樣本與原音差異為 0；那一句的目標頻帶衰減 26.5 dB；總延遲 1012.5 ms |
| v0.4.6 `deep-wide`（1–6.5 kHz，Rust 版，合成測試語音）：目標頻帶衰減 / 總能量 / 頻帶外 LSD | ≥ 40 dB / −0.4 dB / 0.00 dB |
| `heysiri` 模式（v0.4.6） | 總延遲 72.5 ms。沒看過的合成「Hey Siri」92% 被完整處理；真人中文朗讀只有 1.4% 的時間被處理（舊的 `sibilant` 模式約 19%）。強度 `early` 的「Hey」那一關：91% 的「Hey + s…」在 /s/ 之前觸發（中位數 0.10 秒前），真人中文每分鐘誤觸發 3 次。細節見 [`heysiri` 模式的偵測器](siri-guard-research.md#heysiri-模式的偵測器) |
| 對開源喚醒詞偵測器的效果 | 見 [Hey Siri 研究與實測：實測效果](siri-guard-research.md#實測效果) |

## 已知限制

- 回聲消除只能消掉線性的部分：喇叭失真、機殼共振消不掉，喇叭越大聲殘留越多。
- WebRTC 引擎的參數沒辦法調，例如雙講時的積極程度。
- Speex / NLMS 只在 16 kHz 處理，你的聲音頻寬會變成約 7 kHz。
- 「系統主音量」大幅改變時，回聲消除可能要幾秒重新收斂。
- 程式沒在跑時，`CABLE Output` 沒有聲音。
- Rust 版還沒在實機上長時間使用過，見 [Rust 版（v0.4.0）](#rust-版v040)。
- Hey Siri 防護的限制見[這裡](siri-guard-research.md#限制)。
